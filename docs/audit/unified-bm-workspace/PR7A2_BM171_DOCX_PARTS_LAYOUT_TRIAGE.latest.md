## 5. Decision required — there are two defensible paths, NOT one

### Path A — keep notes 12/13 as `EXPECTED_BY_TEMPLATE` (mirror BM-001)

- Evidence: BM-001's visual sign-off treats these drafter-note
  paragraphs as expected-by-template. The locked contract for BM-171
  has the same shape (no slot binds to them; the paragraphs come from
  the template body).
- Implementation: zero. Document the exception in the BM-171 visual
  sign-off packet and get a Planner eyeball confirming this is OK for
  the legal workflow.
- Risk: if the Vietnamese prosecution workflow treats the same notes
  differently for BM-171 than for BM-001 (different stage, different
  audience), the BM-001 precedent may not generalize. **This must be
  answered by a domain decision, NOT by the agent.** Until then, Path A
  is provisional.

### Path B — suppress notes 12/13 in the final DOCX

- Evidence: the locked contract has 34 `docxSlots` and NONE reference
  P0080/P0081 (notes 12/13). The notes are template residue that should
  not appear in the legal-document output the VKS sends out.
- Implementation options:
  1. Mutate the **normalized DOCX** (forbidden per AGENTS.md "Do NOT
     mutate 213 locked DOCX contracts/templates unless explicitly
     scoped"). Needs explicit user authorization.
  2. Add a **per-BM suppression list** in the renderer / contract
     render plan that drops paragraphs whose only text is a drafter
     note. Requires extension to the generic engine — a PR6G-level
     change, NOT a BM-171 hotfix.
  3. Add a **per-BM body-tail-clipper rule** in the BM-171 style profile
     (e.g. "drop trailing paragraphs that begin with `<w:vertAlign
     w:val="superscript"/>` followed by a `Ghi …` body"). This is the
     most defensible scoped fix because it (i) lives in the per-BM
     style profile the BM-001 lesson already created as the place for
     per-BM rendering rules, and (ii) does not touch the normalized
     DOCX.
- Risk: option (3) requires a new rule type in the PR6G.4 style-rule
  engine (paragraph-drop rule). That engine is generic; adding a new
  rule kind is a generator change and re-opens PR6G.4.

**Both paths require an explicit Planner decision.** The triage refuses
to silently pick one. The `audit-bm-final.mjs` evidence note that says
"word/footnotes.xml carries only Word-emitted separator entries" is
correct in spirit (no real Word footnotes) but incorrect in wording
(BM-171 has no footnotes part at all). The PR6G.2 harness output for
BM-171 should report `footnotes: NOT_PRESENT` rather than
`footnotes: NOT_APPLICABLE_BY_TEMPLATE`.

## 6. Spacing diagnosis — Page 1 huge blank before `QUYẾT ĐỊNH:`

The rendered DOCX paragraph index walk (rendered-body-layout.json) shows:

| idx | text | spacing note |
|---:|---|---|
| 14 | `Độc lập - Tự do - Hạnh phúc` | centered, bold, 14pt |
| 15 | (line drawing — the underline beneath paragraph 14) | `<w:drawing>` shape with `<a:prstGeom prst="line">` — Word-rendered underline |
| 16 | empty | `<w:p><w:pPr>...` empty paragraph |
| 17 | empty | `<w:p><w:pPr>` empty paragraph, italic run default |
| 18 | `TP. Hồ Chí Minh, ngày 04 tháng 07 năm 2026` | centered, italic, 14pt |
| 19 | `QUYẾT ĐỊNH` | centered, bold, 14pt; `w:beforeLines="50" w:afterLines="50"` |
| 20 | `TRẢ LẠI TÀI SẢN` | centered, bold, 14pt |
| 21 | empty | center-aligned; `w:beforeLines="50"` |
| 22 | empty run | center-aligned; bold run with empty text |
| **23–28** | **6 empty paragraphs** | `w:jc="both"`, first-line indent 720 twips, **default `<w:spacing w:before="192" w:beforeLines="50" w:after="192" w:afterLines="50" w:line="320" w:lineRule="exact"/>`** |
| 29 | empty | last legal-basis-style empty para |
| 30 | `QUYẾT ĐỊNH:` (lowercase form, bold-centered, with colon) | the body-title-of-the-decision-block, NOT the document title |
| 31 | `Điều 1. Trả lại tài sản sau đây:` | the article heading |

**Cause of the visible huge blank**:

1. Paragraphs **21–29** are 9 consecutive empty paragraphs inherited
   from the source DOCX. In the source DOCX, these correspond to
   `{{official.issuerTitle}}` + `{{legalBasis.procedureArticlesLine}}`
   + ... + `{{assetReturn.considerationLine}}` — the **legal-basis
   placeholder block** (locked contract slots 5–12). In the canonical
   signoff fixture, **27 of 34 slots are empty** (`missingRequiredCount:
   27` per `document-xml-inspection.latest.json`). After docxtemplater
   expansion, each empty placeholder leaves its `<w:p>` paragraph
   intact and the run becomes an empty `<w:t/>`.
2. Each of those empty paragraphs has `w:spacing w:before="192"
   w:beforeLines="50" w:after="192" w:afterLines="50" w:line="320"
   w:lineRule="exact"/>` — that's 50/100 of a line of space before AND
   after, plus a fixed line height of 320 twips (16pt). 9 paragraphs ×
   (50 + 16 + 50)/100 ≈ ~1.04 inches of empty space added BELOW
   paragraph 18 (the date line) and ABOVE paragraph 30 (the body
   `QUYẾT ĐỊNH:`).
3. The "underline drawing" (paragraph 15) is a `<w:drawing>` element
   with `cx="2160270"` EMU width — about 5.7 cm — and zero height
   (`cy="0"`). The `<a:ln w="9525">` defines the line thickness
   (~0.75pt). This is the rule beneath "Độc lập - Tự do - Hạnh phúc"
   and it adds visible vertical space because of how Word pagination
   treats wps:wsp elements with positioning. **This is unique to
   BM-171's normalized template** and is inherited from the legacy
   `.doc` → `.docx` normalization.

**Diagnosis**: not a renderer bug, not a style-profile bug. **Source
DOCX structure** (legal-basis placeholder block left empty + the
positional line drawing for the rule) is the direct cause.

**Two sub-fixes possible, but again require explicit user policy**:

- Sub-fix 1 (path-of-least-resistance): the canonical fixture fills
  ONLY 4 slots (`document.issuePlaceAndDateLine`,
  `assetOwner.dateOfBirthText`, `assetOwner.identityIssuedDateText`,
  `recipients.archiveLine`). If the future BM-171 panel exposes those
  27 legal-basis slots in the UI, the user fills them in their case
  and the empty paragraphs become text and the visual collapses
  naturally. **No renderer change.** This is the only fix that
  doesn't require a locked-DOCX or generic-engine mutation.
- Sub-fix 2: add a `<w:collapseEmptyParagraphs>` style-profile rule in
  the BM-171 profile that drops paragraphs whose text is `<w:t/>` AND
  whose `w:pStyle` matches one of the legal-basis-placeholder styles.
  Requires a new style-rule kind in the PR6G.4 engine — reopens PR6G.4.
- Sub-fix 3 (FORBIDDEN): edit the normalized DOCX to remove the
  paragraphs. AGENTS.md hard-boundary forbids this without explicit
  scope.

| 86 | `12 Ghi cụ thể cơ quan...` |
| 87 | `13 Ghi chức danh người ký` |

Source DOCX has **the same 88 paragraphs at the same indices** (modulo
the emptied placeholders after docxtemplater expansion). The page break
to page 2 is **a Word-pagination artifact of paragraph overflow** with
no `<w:br w:type="page"/>` and no `lastRenderedPageBreak` marker in the
package.

The page bottom margin is **`w:bottom="288"` twips ≈ 0.5 cm** (very
tight). When Word/Office renders A4 (16834 twips tall) with 864-top +
288-bottom + a ~30% body fill of `{{placeholder}}` paragraphs each
carrying `w:before/after` spacing, the body overflows past the bottom
margin and Word pushes a few trailing items (notes 12/13, possibly the
`Nơi nhận` block) to page 2.

**Why does `Nơi nhận` move to page 2 too in some renders?** The
extracted text shows `Nơi nhận:` on its own line (paragraph 46 in our
index) followed by `Lưu: HSVA, HSKS, VP.` (paragraph 48). The Planner
eyeball reported seeing both in the page-2 area in the actual rendered
Word render — that means the **page-1 body** already exhausted the
vertical space BEFORE paragraph 46 in their rendering, and the
`Nơi nhận` + `Lưu:` block + 37 trailing empty paragraphs + notes 12/13
all spilled to page 2 together.

**Diagnosis**: not a renderer bug. The legacy `.doc` template had a
small body region + a wide footer (notes 12/13 + Mẫu số 171/HS banner)
which Word paginates dynamically. The empty `{{placeholder}}` paragraphs
each carry `w:beforeLines/afterLines="50"`, and the canonical signoff
fills only 4 of 34 slots, leaving the body shorter than Word expects
for the bottom margin. The overflow is structural.
